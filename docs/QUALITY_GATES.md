# JARVIS V1 Quality Gates

These are universal completion rules for major product slices, owner-approved integration/stabilization interludes, and future JARVIS-generated engineering candidates. Code existing or unit tests passing is never sufficient by itself.

## 1. Scope Gate

- Implementation matches the approved slice/interlude/EngineeringChange.
- Explicit non-scope remains out.
- No unrelated future capability is smuggled in.
- No old-JARVIS runtime dependency is introduced.
- Partial foundations are not mislabeled as completion of later roadmap steps.
- A JARVIS-generated candidate remains bounded to the approved architecture objective; autonomous implementation is not permission to expand scope.

## 2. Ownership and Architecture Gate

- Every responsibility has one authoritative owner.
- Conversation/context/memory/authority state is not duplicated.
- Provider-specific mechanics remain behind narrow replaceable boundaries where practical.
- Multiple capabilities reuse canonical capability/authority contracts rather than inventing parallel routers or permission systems.
- Repair, capability acquisition and self-improvement reuse shared WorkItem/EngineeringChange/Authority/verification boundaries rather than becoming competing autonomous systems.
- Development/repair tooling does not silently become normal user-facing authority.
- `CURRENT_ARCHITECTURE.md` reflects only accepted running architecture.
- Material implementation starts only after an architecture decision is owner-approved under the active governance contract.

## 3. Automated Test / CI Gate

Tests should cover important contracts, real subsystem boundaries, failure/timeouts, replay/staleness, malformed provider output, unauthorized execution, and previously accepted regressions.

The current repository Code Quality workflow includes:

- Ubuntu Ruff format check;
- Ubuntu Ruff lint;
- Ubuntu Python install with the accepted development/Hands test extras;
- Playwright Chromium provisioning and real headless-launch smoke;
- full repository `pytest` suite on Ubuntu;
- Windows .NET 9 build of `Jarvis.WindowsHelloVerifier`;
- Windows Hello helper JSON contract probe;
- production self-contained Windows Hello helper publish + JSON contract probe;
- Windows unified Hands dependency probe;
- Windows multilingual Hands/grounding/UTF-8 regressions;
- Windows DPAPI smoke/regressions.

A green PR head is necessary but not sufficient when Windows hardware, provider behavior, Pocket 3 transport, audio, UI Automation, network devices or other real-world behavior cannot be proven by CI.

Generated tests are useful evidence but may not be the sole verifier when the same reasoning system generated both the candidate and the success criterion.

## 4. Truthfulness and Verification Gate

- Never report completion when execution did not complete.
- Failure, partial completion, unavailable providers, stale evidence and unverified results remain explicit.
- Fallbacks preserve the original goal.
- Current/fresh claims have source/freshness evidence when required.
- Mutation success requires authoritative/postcondition evidence where practical.
- Physical behavior alone does not substitute for trusted state evidence when stronger evidence exists; for example, camera movement alone is not Pocket native `LOCKED`.
- Model confidence is never equivalent to verification.
- A candidate generated by one model may be reviewed by models, but final success must be grounded in independent/deterministic evidence appropriate to the change.
- New capabilities must state their proven support matrix and known limitations rather than infer unsupported operations.

## 5. Authority and Risk Gate

### Low-risk reads

Bounded scope, policy permission, truthful unavailable state, and no repetitive unnecessary approval.

### Reversible local actions

Clear user intent, bounded semantic executor rather than arbitrary shell, proportional confirmation, and rollback/undo where practical.

### Persistent writes / external communication

Separate read/draft/proposal from commit authority; exact target/content binding; explicit approval where required; preview/draft before irreversible commit where practical.

### Destructive / financial / security / self-modifying actions

Remain blocked until separately governed. They require exact-action binding, strong trust, dry-run/backup/rollback where relevant, and no weakening merely for convenience.

Universal rules:

- capabilities cannot self-authorize;
- provider/model/UI cannot bypass JARVIS authority;
- identity evidence is not execution permission;
- one approval cannot be reused for materially different work;
- unrestricted arbitrary shell/PowerShell is not a general model capability;
- unrestricted package installation is not a general model capability;
- unrestricted network/device discovery is not a general model capability;
- secrets/sensitive payloads are not unnecessarily logged or placed in normal model context;
- a development candidate cannot grant itself new production credentials, permissions or network scope;
- protected-main merge remains an explicit owner-governed promotion step.

### T2 convenience rule

General biometric/voice-derived T2 remains deferred. Any Hands same-session T2 convenience must originate from a successful direct-user Windows Hello/T3 verification, obey its bounded absolute lifetime/session/origin rules, and never replace a required T3 challenge.

## 6. Privacy, Secrets and Data Lifecycle Gate

- Persist only what accepted behavior requires.
- Separate session context from durable memory.
- Raw audio/full transcripts/provider payloads are not retained by default.
- Durable personal memory has correction/removal paths.
- Secrets/tokens do not enter normal prompts/logs unnecessarily.
- Future credential-requiring capabilities should use a SecretBroker/local trusted entry surface and opaque scoped secret references rather than prompt-visible plaintext.
- Secret usage is scope-bound and auditable without logging the plaintext.
- Screenshots sent for visual Computer Use are bounded to the accepted target-window contract.
- Observability records operational evidence without becoming surveillance.
- Provider-side retention limitations are not misrepresented as JARVIS deletion guarantees.

## 7. Dependency and Supply-Chain Gate

Any new third-party dependency, SDK, model artifact or executable introduced by autonomous engineering must have durable provenance appropriate to its risk.

At minimum, where applicable:

- canonical package/source identity;
- exact resolved version;
- source/repository or registry origin;
- cryptographic digest for acquired artifacts where practical;
- license/policy compatibility;
- dependency purpose and owning capability/change;
- reproducible acquisition/build information where practical;
- vulnerability/security review proportional to risk;
- no hidden dependency acquisition performed through unrestricted shell authority.

The preferred architecture is a governed `DependencyBroker` plus staged artifact cache consumed by isolated environments.

## 8. Capability Package Gate

A dynamically acquired capability cannot be considered ready for promotion without a normalized capability manifest or equivalent canonical record containing, as applicable:

- capability ID/version/purpose;
- supported operations;
- compatible device/service/provider versions;
- required permissions/network scope;
- dependency identities/versions;
- secret requirements without plaintext;
- resource requirements;
- health probes;
- verification contracts;
- disable/rollback procedure;
- source/build provenance;
- owner acceptance evidence;
- lifecycle state.

Capability registration never bypasses normal per-action Authority.

## 9. Resilience Gate

- Provider/network/audio/device failures do not corrupt canonical state.
- Resources are cleaned up on shutdown/cancel/reconnect.
- Recovery remains bounded and does not loop blindly.
- Stale evidence is invalidated after transport/session rebuild.
- Recovery/fallback does not weaken identity, permission or truthfulness boundaries.
- Newly introduced authority has a disable/rollback path.
- A failed engineering experiment cannot mutate protected production state.
- A provider/model outage cannot disable already-accepted deterministic production repair.

## 10. Performance and Baseline Gate

Measure user-critical paths before optimizing. Relevant measures include voice latency, planning/execution latency, startup time, memory retrieval, CPU/RAM/GPU, perception cadence, provider latency and background resource use.

Accepted optimizations must preserve functional/security invariants. Historical optimization branches are not automatically mergeable merely because one experiment performed well; proven pieces may be selectively recovered onto current main.

For an improvement/evolution candidate, "tests pass" is insufficient. Compare against the accepted production baseline on the metrics relevant to the claimed improvement and reject material regressions that violate the approved objective or invariants.

## 11. Human / Hardware Acceptance Gate

Major user-facing behavior must be exercised normally on the owner machine when synthetic tests cannot prove the experience.

Acceptance should validate real behavior such as conversation, interruption, authority UX, no duplicate mutations, truthful failures, Pocket tracking/reacquisition/recenter, visual containment, useful latency, network-device behavior and other physical outcomes—not merely that an API returned success.

For hardware-in-the-loop work, JARVIS may ask the owner for bounded observations such as whether a TV powered on or whether a gate alert fired. The observation becomes typed acceptance evidence and does not replace all automated verification.

## 12. Autonomous Engineering Change Gate

Before a JARVIS-generated repair, integration, new capability or improvement candidate is ready for promotion, its durable EngineeringChange (or equivalent accepted object) must preserve:

- trigger/owner goal;
- research evidence;
- architecture decision and owner approval;
- WorkItems/steps executed;
- dependency/secret requirements;
- source diff/candidate identity;
- tests/verification evidence;
- owner-machine/hardware acceptance where required;
- known limitations;
- rollback/disable plan;
- PR/CI state;
- final promotion decision;
- production observation after deployment when applicable.

A restart/provider failure must not be able to skip architecture, acceptance or promotion gates.

## 13. Documentation Reconciliation Gate

Before a step or major integration/stabilization interlude is considered closed:

- `CURRENT_PLAN.md` reflects accepted current state, deferrals, superseded/rejected work and the next active slice;
- `CURRENT_ARCHITECTURE.md` reflects what actually runs;
- `ROADMAP.md` distinguishes complete steps from partial foundations pulled forward;
- `PRODUCT.md` capability statuses match reality (`DONE`, `BOUNDED`, `PARTIAL`, `ACTIVE`, `PLANNED`, `RETIRED`);
- `PROJECT_STATE.md` records whether work is accepted, deferred, superseded or rejected, while detailed historical evidence remains available in Git history;
- `GOVERNED_AUTONOMOUS_ENGINEERING_MASTER_PLAN.md` remains the north-star architecture for owner-directed autonomous engineering;
- the specialized `SELF_REPAIR_AND_EVOLUTION_MASTER_PLAN.md` remains aligned under that north star;
- durable architecture decisions receive an ADR when future work could otherwise misunderstand the boundary;
- README-level status is not materially stale;
- historical research files may retain their original experimental status, but a later accepted record must clearly supersede them for current truth.

If status summaries disagree, `CURRENT_PLAN.md` is authoritative for the active phase and the drift must be corrected before closure.

Git history is the archive; do not create duplicate `FINAL`/`V2` histories merely to preserve old wording.

## 14. Cleanup Gate

- rejected implementations are removed from production paths;
- dead scaffolding/debug artifacts are not retained casually;
- abandoned experiments do not remain active;
- compatibility paths have an explicit purpose;
- stale branches/PRs are labeled/recorded as superseded rather than treated as hidden future integration work;
- rejected/stale EngineeringKnowledge cannot silently re-enter accepted retrieval or authority paths.

## 15. Final Goal Coherence Gate

Every slice must preserve one coherent Personal Intelligence Runtime. Ask whether it:

- composes with canonical conversation, memory, truthfulness, authority, observability and capability boundaries;
- moves JARVIS toward accepting owner intent and autonomously performing the required governed engineering;
- reduces manual engineering burden on the owner without transferring owner authority to the model;
- reuses canonical WorkItem/EngineeringChange/knowledge/verification infrastructure rather than creating a parallel system;
- remains understandable to the owner;
- preserves provider replaceability;
- keeps consequential/self-modifying authority governed.

A slice that makes a local feature work but makes the final autonomous-engineering architecture harder to reach has not passed this gate without an explicit owner-approved tradeoff.

## 16. Git and Promotion Gate

Normal lifecycle:

```text
requirements / owner goal / incident
-> research
-> technology decision
-> architecture
-> owner approval
-> isolated implementation
-> automated validation
-> real human/hardware validation where required
-> corrections
-> owner acceptance
-> documentation reconciliation
-> PR/review
-> exact-head required checks
-> explicit merge approval
-> protected-main merge
-> production verification/observation
```

Do not merge merely because a branch is green. Hardware acceptance and explicit owner authorization remain required where the active slice calls for them.

Development supervisors/agents may detect, research, implement, test and prepare changes, but they do not weaken repository governance or gain autonomous protected-main merge authority.
